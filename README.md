### 📋 Що зробити

**1. Функціональний інтерфейс `IdentityExtractor<T>`** — як витягти з обʼєкта його унікальне поле:

```java
@FunctionalInterface
public interface IdentityExtractor<T> {
    String identityOf(T item);
}
```

Реалізації передаєте лямбдами — окремих класів під це не пишете.

**2. Клас `GenericRepository<T>`** з таким мінімумом:

```java
public GenericRepository(String name, IdentityExtractor<T> extractor)

public void            add(T item)
public boolean         addIfAbsent(T item)
public void            addAll(Collection<T> items)
public boolean         removeByIdentity(String identity)
public Optional<T>     findByIdentity(String identity)
public List<T>         findAll()
public int             size()
```

Всередині зберігаєте елементи в `Map<String, T>`, де ключ — identity. Яку саме реалізацію `Map` взяли — ваш вибір, на захисті поясните.

- `add(null)` і елемент із порожньою identity → `IllegalArgumentException`;
- `findByIdentity` повертає `Optional<T>`, а не `null`;
- `findAll()` повертає такий список, яким зовнішній код не може зіпсувати стан репозиторію.

**3. Контракт дублікатів.** `add` з identity, яка вже є, кидає власне **unchecked** `DuplicateIdentityException` (наслідує `IllegalStateException`); у повідомленні — identity й назва репозиторію. `addIfAbsent` на тому самому обʼєкті нічого не кидає й повертає `false`.

Унікальність забезпечує репозиторій, а не сутність: конструктори та компактні конструктори з ЛР1–ЛР2 про дублікати нічого не знають і не дізнаються.

**4. Перевірте репозиторій на трьох різних типах** вашого домену — щонайменше один record і щонайменше один ✎-клас зі змінюваними полями. Для кожного типу — свій екземпляр репозиторію і своя лямбда-`IdentityExtractor`.

Для ✎-класу беріть identity з поля, яке після додавання не змінюється.

**5. Наповніть один репозиторій із CSV-файла ЛР3.** Додайте у файл щонайменше один рядок із уже наявною identity, щоб шлях із дублікатом спрацьовував на справжніх даних, а не лише в `Main`.

**6. Логування через SLF4J** — ті самі три рівні, що й у ЛР3: `INFO` на успішні операції, `WARN` на відхилений дублікат і ненайдений елемент, `ERROR` там, де виключення не ковтається, а летить далі. Одну й ту саму подію логуйте в одному місці: або в репозиторії, або у викликача, але не двічі.

**7. Тести на JUnit 5, щонайменше сім:**

- `add` + `findByIdentity` знаходить доданий елемент;
- `findByIdentity` на відсутній identity повертає порожній `Optional`;
- повторний `add` кидає `DuplicateIdentityException`;
- `addIfAbsent` повертає `false` і не змінює `size()`;
- `removeByIdentity` на наявному й на відсутньому елементі;
- спроба змінити результат `findAll()` не змінює репозиторій;
- той самий клас репозиторію працює щонайменше з двома різними типами.

**8. Оновіть `Main`.** Показати треба:

1. три репозиторії різних типів і пошук за identity — знайдено і не знайдено;
2. наповнення репозиторію з CSV-файла;
3. додавання дубліката через `add` (із перехопленням) і через `addIfAbsent` — різницю видно у виводі;
4. видалення наявного й відсутнього елемента;
5. логування всіх трьох рівнів.

**9. Порівняйте пошук у `Map` і в `List`.** Окремий клас — наприклад, `SearchBenchmark` із власним `main` — у тому самому пакеті, що й `GenericRepository`. Сам репозиторій не змінюється, лінійний пошук туди не додається.

Згенеруйте 100 000 обʼєктів одного типу й покладіть їх у репозиторій. Список для лінійного пошуку візьміть із `findAll()` **один раз, до вимірювань** — усередині циклу ви міряли б копіювання, а не пошук.

Лінійний пошук пишете самі, приватним статичним методом того ж класу, з тим самим `IdentityExtractor`:

```java
private static <E> Optional<E> linearSearch(
        List<E> items, String identity, IdentityExtractor<E> extractor) {
    for (E item : items) {
        if (identity.equals(extractor.identityOf(item))) {
            return Optional.of(item);
        }
    }
    return Optional.empty();
}
```

Три сценарії пошуку — перший елемент, останній, відсутній — обидвома способами. Перед замірами зробіть прогін на прогрів, кожен замір повторіть кілька разів і беріть медіану або мінімум, а не перше число.

Результат — таблицею в `README.md` гілки `lab4` плюс два-три речення висновку: де різниця величезна, де її майже немає і чому.

### Реалізація ЛР4 і локальна перевірка

`GenericRepository<T>` зберігає елементи в `LinkedHashMap<String, T>`. Пошук відбувається за ключем, а порядок додавання зберігається, тому перший і останній записи в списку мають визначений порядок.

`addAll(Collection<? extends T>)` приймає колекції підтипів, а `IdentityExtractor<? super T>` дозволяє використати функцію для спільного надтипу. `addAll` додає елементи послідовно через `add`, тому при помилці раніше додані елементи залишаються в репозиторії.

`findAll()` повертає незмінний знімок складу колекції. Самі сутності не копіюються, тому зміна підписки `MusicUser` видима через збережений об’єкт. Для пошуку користувача використовується незмінне поле `accountEmail`.

```bash
./gradlew clean build
./gradlew run
./gradlew benchmark
```

На Java 21 пройшли всі 29 тестів, з них 12 перевіряють репозиторій. Демонстрація створює репозиторії для `Artist`, `MusicUser` та `Album`, відхиляє повторний `ART-01` із CSV й показує різницю між `add` та `addIfAbsent`. Некоректне додавання `null` записується як `ERROR` перед передаванням винятку викликачу, а очікувані дублікати й відсутні записи — як `WARN`.

Зауваження до ЛР3 враховані — кожен тест має англійський `@DisplayName`, очікувані помилки CSV і сеттера логуються без стектрейсу, відсутній файл окремо обробляється як `NoSuchFileException` на рівні `WARN`. Модель і компактні конструктори збережені.

### Порівняння пошуку

Фактичний запуск `./gradlew benchmark` виконано 24.11.2026 у WSL із Java 21. Використано 100 000 виконавців, п’ять прогрівальних раундів і дев’ять вимірювань по 100 пошуків для кожного сценарію. У таблиці наведено медіанний час одного пошуку в наносекундах.

Список отримано через `findAll()` один раз до вимірювань. Логування вимкнене лише для задачі `benchmark` через `logback-benchmark.xml`, щоб консольний вивід не впливав на час пошуку. Порядок вимірювання `Map` і `List` чергується, а результати пошуків перевіряються та використовуються в програмі.

| Сценарій | Map, нс/пошук | List, нс/пошук |
| --- | ---: | ---: |
| Перший елемент | 90.6 | 67.2 |
| Останній елемент | 181.5 | 665011.6 |
| Відсутній елемент | 150.4 | 367906.4 |

Для першого елемента список виявився трохи швидшим, бо йому достатньо одного порівняння. Для останнього й відсутнього елементів список перебирає всі записи, тоді як `Map` знаходить потрібний ключ за середній сталий час. Конкретні числа залежать від JVM і навантаження комп’ютера, тому під час повторного запуску вони можуть змінитися.
